🏗️ 1. Visão Geral do Sistema

HiveMI é uma plataforma de orquestração de agentes AI. Cada agente roda em uma VM isolada na nuvem com sua própria instância do OpenClaw. O sistema central (control plane) gerencia o ciclo de vida dos agentes, distribui tarefas e coleta métricas.

📦 2. Apps (Serviços Runtime)
🖥️
Dashboard
apps/dashboard · Next.js 16 · :3000
Frontend + API Proxy

Interface web do HiveMI. React 19 + Tailwind 4 + Lucide icons. Server-side API routes fazem proxy transparente para Registry (:4001) e Manager (:4000).

Páginas: Home (agents), Agent Detail, Tasks, Teams, Roles, Settings (7 seções), Logs

Modais: Deploy Agent, Create/Edit Role, Create/Edit Team, Create Task, Task Detail, Confirm Dialog

16 componentes · 7 páginas · 35+ API routes (proxy)

⚙️
Manager
apps/manager · Hono · :4000
Orchestrator

Orquestrador central. Coordena deploys (5 fases), gerencia demandas (task assignment), infra (reconciliation, costs) e status geral do cluster.

Deploy Orchestrator: Provisioner → Cloud-init → SSH Bootstrap → Configure → Register (~917 linhas, maior arquivo do projeto)

Dependências: @hivemi/protocol, @hivemi/provisioner, @hivemi/bootstrapper

📋
Registry
apps/registry · Hono · :4001
Source of Truth

Banco de dados central e API CRUD. Todas as entidades passam por aqui. Postgres via Drizzle ORM. Auth via Bearer token (HIVEMI_SECRET).

Rotas: agents (register/upsert), roles, teams, tasks (queue + CRUD), logs (batch), deploys, heartbeat, telemetry, discovery, cloud settings

Background jobs: offline detection (agents sem heartbeat), lock timeout (tasks travadas)

9 tabelas · 8 route files · Seed data (4 roles + 2 teams + 4 agents)

📚 3. Packages (Bibliotecas Compartilhadas)
📐
protocol
@hivemi/protocol · 884 LOC

Contratos compartilhados do sistema. Schemas Zod para todas as entidades, middleware de auth, config types.

Schemas: Agent, Role, Team, Task, Log, Deploy, Telemetry, Heartbeat, P2P Messages

Usado por: todos os outros packages e apps

🤖
agent-daemon
@hivemi/agent-daemon · ~3k LOC

Daemon que roda em cada VM agent. Faz polling de tasks, executa via OpenClaw, reporta resultados, envia heartbeats e telemetria.

Módulos: task-poller, task-executor, openclaw-client, registry-client, p2p-client, p2p-handler, telemetry, output-parser

☁️
provisioner
@hivemi/provisioner · ~1.8k LOC

Abstração de cloud providers. Cria/destrói VMs, gerencia SSH keys, firewalls, reconciliation de infra, estimativa de custos.

Providers: DigitalOcean (586 LOC, completo), GCP (82 LOC, stub)

Features: reconciliation (orphaned VMs, phantom agents, IP mismatch), cost estimation

🔧
bootstrapper
@hivemi/bootstrapper · ~1.4k LOC

Configura VMs após provisioning. SSH remoto, instala OpenClaw, configura daemon, injeta secrets, espera registration no Registry.

Fases: cloud-init (user-data), configure (SSH + OpenClaw setup), wait-registration

Secrets: envfile (.env) e 1Password (service account)

⚡
agent-runtime
@hivemi/agent-runtime · 249 LOC

Runtime helpers para agentes. Logger padronizado, types compartilhados.

Minimal — pode ser absorvido

💻
cli
@hivemi/cli · 344 LOC

CLI para interagir com o cluster. Comandos para gerenciar agents, tasks, deploys via terminal.

🧠
llm
@hivemi/llm · minimal

Abstração de LLM providers. Atualmente mínimo — agents usam OpenClaw que já abstrai os LLMs.

Minimal — pode ser absorvido ou removido

🚀 6. Fluxo de Deploy

Deploy de um agent é um processo de 5 fases gerenciado pelo Manager via DeployOrchestrator. Cada fase é registrada no Registry com status e timestamps.

      participant M as ⚙️ Manager
      participant P as ☁️ Provisioner
      participant B as 🔧 Bootstrapper
      participant R as 📋 Registry
      participant VM as 🤖 Agent VM

      U->>D: Click "Deploy Agent"
      D->>M: POST /api/deploy
      M->>R: POST /api/deploys (register)
      M->>R: GET /api/settings/cloud

      rect rgb(30, 30, 46)
        Note over M,VM: Fase 1: Provisioning
        M->>P: createInstance(spec)
        P->>VM: Create VM (DigitalOcean API)
        P->>P: waitReady(instanceId)
        P-->>M: { ip, instanceId }
      end

      rect rgb(30, 30, 46)
        Note over M,VM: Fase 2: Installing
        M->>B: bootstrap(config)
        B->>VM: SSH: install OpenClaw
        B->>VM: SSH: install daemon
      end

      rect rgb(30, 30, 46)
        Note over M,VM: Fase 3: Configuring
        B->>VM: SSH: write openclaw.json
        B->>VM: SSH: write secrets (.env)
        B->>VM: SSH: start daemon
      end

      rect rgb(30, 30, 46)
        Note over M,VM: Fase 4: Registering

📋 7. Fluxo de Tasks (Pull Model)

Tasks usam um modelo pull: agents fazem polling do Registry com SELECT FOR UPDATE SKIP LOCKED para claim atômico. Isso evita race conditions e garante que cada task é processada por exatamente um agent.

    sequenceDiagram
      actor U as 👤 Usuário
      participant D as 🖥️ Dashboard
      participant M as ⚙️ Manager
      participant R as 📋 Registry
      participant VM as 🤖 Agent Daemon

      U->>D: Create Task (modal)
      D->>M: POST /api/demands
      M->>R: POST /api/tasks (create, status: queued)
      M->>R: GET available agent for team
      alt Agent disponível
        M->>R: PUT /api/tasks/:id (status: locked)
        M->>R: PUT /api/agents/:id (status: working)
      else Sem agent
        Note over M: Task fica queued
      end

      loop Polling (10s interval)
        VM->>R: GET /api/tasks/next?role=X&agentId=Y
        R->>R: SELECT FOR UPDATE SKIP LOCKED
        R-->>VM: task (or 204 No Content)
      end

      VM->>VM: Execute task via OpenClaw
      VM->>R: PUT /api/tasks/:id/complete
      Note right of VM: { status, output, artifacts, subtasks }
      R->>R: Update task + agent status → idle
🔗 8. Comunicação P2P entre Agents

Agents podem se comunicar diretamente via HTTP na rede privada VPC. O Registry funciona como service discovery — um agent resolve o endpoint do outro antes de enviar mensagens.

Protocolos: task-handoff (delegar task), ask (perguntar algo), inform (notificar), review-request (pedir code review)

Flow: Agent A → GET /api/agents/:id/endpoint → resolve IP:port → POST direto no Agent B

📊 9. Telemetria & Monitoramento
💓
Heartbeat

Daemon → Registry a cada 30 segundos. Inclui status, currentTaskId. Registry marca agent como unreachable se 3 heartbeats consecutivos falharem.

📈
Telemetry

Daemon → Registry a cada 60 segundos. Métricas de infra (CPU, RAM, disk), LLM (requests, tokens, latência), tasks (completed, failed, active), daemon (uptime, version).

📝
Log Shipping

Daemon → Registry a cada 5 minutos (batch). Só envia warn, error, lifecycle. Armazena em tabela logs com metadata JSONB.

🔍
Offline Detection

Background job no Registry. Verifica last_heartbeat dos agents. Se > 2 minutos sem heartbeat → status muda para unreachable.
